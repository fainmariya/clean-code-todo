# AI Code Review Instructions

## 1. Цель

Провести Code Review JavaScript-кода приложения Clean Code Todo.

Оценить качество кода с точки зрения принципов Clean Code и выявить конкретные проблемы, которые могут влиять на читаемость, поддержку и надёжность приложения.

Проверить следующие категории:

- Naming — понятность названий переменных и функций.
- Functions — размер функций, ответственность и сложность.
- DRY — дублирование кода и логики.
- Comments — лишние, устаревшие или вводящие в заблуждение комментарии.
- Dead Code — неиспользуемый код.
- Error Handling — обработка ошибочных и нестандартных ситуаций.

## 2. Границы проверки

- Анализировать текущие файлы проекта, прежде всего `app.js`.
- Учитывать существующую функциональность Todo-приложения.
- Не редактировать и не создавать файлы самостоятельно.
- Не менять архитектуру приложения без обоснованной необходимости.
- Не добавлять библиотеки и зависимости.
- Не предлагать изменения только ради изменения стиля.
- Не изменять конфигурацию ESLint, Prettier, Husky и GitHub Actions.
- Не предполагать наличие ошибок без конкретных доказательств.

## 3. Критерий готовности

Ревью считается завершённым, когда:

- Проверены все перечисленные категории.
- Каждое замечание относится к конкретному участку кода.
- Объяснено, почему обнаруженное поведение является проблемой.
- Указаны условия, при которых проблема проявляется.
- Предложен конкретный способ проверки возможного исправления.
- Замечания сгруппированы по категориям и отсортированы по важности.
- Явно отмечены категории, в которых проблем не обнаружено.

## 4. Формат вывода

Предоставить отчёт на русском языке в формате Markdown, предназначенный для файла `review-report.md` в корне проекта.

Для каждого замечания использовать структуру:

### Замечание N: название проблемы

**Категория:** Naming / Functions / DRY / Comments / Dead Code / Error Handling

**Место в коде:** название файла, функция, строка или фрагмент кода.

**Проблема:** что именно не так и почему это важно.

**Условие проявления:** при каких обстоятельствах проблема возникает или становится заметной.

**Как проверить исправление:** конкретные действия или тест, которые позволят убедиться, что проблема устранена.

**Приоритет:** высокий / средний / низкий.

В конце отчёта добавить краткое резюме с количеством найденных проблем по категориям.

Не изменять исходный код. Окончательное решение о принятии или отклонении замечаний принимает разработчик.
